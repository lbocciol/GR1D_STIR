# Task: implement a burning-network integrator on top of a pynucastro-generated Fortran interface

You are working inside a project folder that contains a nuclear reaction network
generated by **pynucastro** (`FortranNetwork`). The network generation is DONE —
do **not** touch or regenerate it. Your job is only to write the **integrator /
driver** that sits between the pynucastro RHS+Jacobian and the hydrodynamics code
(GR1D-style: in with `rho, T, X`, out with the specific energy generation rate).

## Before you write anything

1. **Read the generated interface first.** Open `fortran_interface.f90` (pynucastro
   emits a module called `pynet`) and the companion `wrapper.cpp` /
   `simple_cxx_network`-style C++ files. Determine the **exact** names, argument
   order, argument types (note `iso_c_binding` kinds: `c_double`, `c_int`,
   `value` vs by-reference), and array shapes of:
     - the RHS routine (pynucastro calls it `rhs_f`),
     - the Jacobian routine (`jac_f`),
     - any init routine,
     - the energy-generation routine if one is exposed separately (in recent
       pynucastro the energy release was folded into the RHS module — confirm
       which is the case here),
     - the module name itself and the integer parameter giving the number of
       species (e.g. `nspec` / `number_equations`), and the arrays of `aion`
       (mass numbers) and `zion` (proton numbers).
   **Do not assume the signatures below are correct — verify them against the
   actual generated source and adapt.** The stub file I provide uses placeholder
   signatures and marks every spot you must reconcile with `TODO(verify)`.

2. **Confirm units and variable conventions** used by the generated RHS:
     - Does it evolve molar abundances `Y_i = X_i / A_i` or mass fractions `X_i`?
       (pynucastro RHS works in `Y`.) Convert at the boundary.
     - What are the temperature/density units it expects (CGS: K, g/cc)?
     - What is the sign/units convention of the energy term (erg/g/s)?
   Write these findings as comments at the top of `burn.f90`.

## What to build

Fill in the provided skeleton `burn.f90` (a Fortran module `burn`). Keep the
public surface small and hydro-friendly. Required public routines:

- `burn_init()` — calls the network init once at startup; allocates any module
  scratch; caches `nspec`, `aion`, `zion`.
- `burn_rhs(rho, T, X, dYdt, edot)` — single RHS+energy evaluation (no time
  integration). Wraps `rhs_f` (and the energy routine), converts X<->Y at the
  boundary, returns `dYdt` and `edot = enuc + enu_weak` in CGS (erg/g/s). This is
  the routine the user already sketched; make it correct and unit-consistent.
- `burn_state(rho, T, X_in, dt, X_out, e_released, ierr)` — **the actual
  integrator.** Advance the abundances over a hydro substep `dt` and return the
  updated composition and the **integrated** specific energy released over the
  step (erg/g), plus an error flag. This is the routine hydro calls.

## Integrator requirements

- The system is **stiff**. Use an implicit / BDF method with the **analytic
  Jacobian** from `jac_f`. Default to VODE/DVODE in BDF mode (`MF=21`, analytic
  dense Jacobian) since pynucastro ships/uses VODE; if VODE source is not present
  in the folder, write the wrapper against the standard DVODE interface and leave
  a clear `TODO(build)` note to link it, OR implement a self-contained
  backward-Euler + Newton fallback (provide both behind a parameter
  `integrator_method`).
- Integrate the molar abundances `Y_i`. Provide the RHS and Jacobian callbacks in
  exactly the form the chosen integrator expects (e.g. DVODE's
  `F(NEQ, T, Y, YDOT)` and `JAC(NEQ, T, Y, ML, MU, PD, NRPD)`); these callbacks
  internally call `pynet`'s `rhs_f`/`jac_f`.
- **Temperature handling:** support both modes behind a flag `self_heating`:
    - `self_heating = .false.` (default, simplest): hold `T` and `rho` fixed over
      the substep (isothermal); hydro updates T from the returned energy.
    - `self_heating = .true.`: append a temperature (or internal-energy) equation
      to the integrated system. **The EOS is the hydro code's responsibility** —
      pynucastro does not provide it. So when self-heating, call out to an
      external `eos_*` hook (declare an abstract interface / external procedure
      the host must provide: maps `(rho, e) -> T` and `cv`). Leave this as a
      clearly marked extension point; do not invent an EOS.
- **Energy accumulation:** integrate `de/dt = edot` alongside, or recover the
  released energy from the net binding-energy change over the step
  (`Δe = N_A c^2 Σ_i ΔY_i * (mass excess)_i`), consistent with how the generated
  energy routine defines its zero point. Use whatever the generated routine uses
  so there is no double counting. Document the choice.

## Ye / electron fraction — IMPORTANT physics note (put this logic in the code)

- `Ye = Σ_i Z_i Y_i` is a **derived** quantity, not an independent input. Compute
  it from the composition; do **not** carry it as a separate state variable in the
  network integrator.
- If the generated network contains **only strong + electromagnetic** rates, `Ye`
  is conserved to machine precision automatically — add an **assertion / diagnostic**
  in `burn_state` that checks `|Ye_out - Ye_in|` is below a tolerance and warns if
  not (this catches accidental inclusion of weak rates or integration errors).
- If the generated network **does** contain weak rates (electron/positron capture,
  beta decay — check the rate list / for tabular rates and any `enu_weak`/neutrino
  term in the interface), then `Ye` legitimately drifts. In that case: do **not**
  assert conservation; instead recompute `Ye` from `X_out` and return it as an
  optional output argument `Ye_out` so hydro can hand it to the EOS / NSE solver.
  Add `Ye_out` as an `optional, intent(out)` argument to `burn_state`.
- Add a top-of-module comment block stating the regime assumption: this network
  integrator is intended for the temperature/density regime where the network
  (not NSE) governs the composition; the NSE↔network handoff and any neutrino-
  driven Ye evolution at high density are handled **outside** this module. Do not
  implement NSE here.

## Robustness / hygiene

- Floor tiny/negative abundances (e.g. clamp `Y_i < 0` to 0 after the step) and
  renormalize mass fractions to sum to 1 *only* with a documented, conservative
  scheme (preferably renormalize on `X`, and only if drift exceeds a tolerance).
- Propagate the integrator's return/istate code into `ierr` with meaningful values;
  never silently swallow a failed step.
- All reals `real(8)` / `c_double`. `implicit none` everywhere. No global mutable
  state beyond the cached network constants set in `burn_init`.
- Match the existing code style of `fortran_interface.f90` (free-form, module
  structure, naming).

## Deliverables

- A complete, compiling `burn.f90` with the three public routines above.
- A short `burn_test.f90` driver: initialize, set a simple known state (e.g. pure
  C12/O16 or He4 at a representative `rho`,`T`), call `burn_state` for a few steps,
  print `X_out`, `e_released`, and the `Ye` check. Mirror the style of pynucastro's
  generated `test.f90`.
- Update the Makefile/GNUmakefile to build `burn.f90`, `burn_test.f90`, and link
  the integrator. If you add VODE, add a `TODO(build)` comment showing where its
  sources/library must be provided.
- A few lines at the top of `burn.f90` documenting: abundance convention (Y vs X),
  units, the Ye regime assumption, and which integrator/temperature mode is active.
